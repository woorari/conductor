# GitHub checks and merging

A plan/task approval covers commits, task-branch pushes and PR creation. Main/base merges require the owner’s separate approval of the concrete reviewed PR head. Workers do not merge. The adapter requires `gh` authenticated against github.com; it calls REST through `gh api` without reading or logging the token. Prefer available connector tools for ordinary issue/PR reads and creation; the CLI implements the original Conductor merge checks.

1. Review the task's actual change and checks, then `task_update` it to `green` with its `pr` number and `branch` recorded.
2. Run `merge_check` with `{"task":"id","closes":[12]}`. `closes` must exactly match the PR's closing statements; use `[]` if none. It checks the current PR head, combined check runs and statuses, mergeability, base target, red base CI, dependencies, pause, open problems, and other merge claims. No checks or unread pages never count as green.
3. Show the change and checks to the user and obtain main/base merge approval for this PR/head, unless already explicitly provided. Record it using `approve_merge --caller owner` with `{"task":"id","head":"full-sha-from-merge-check"}`. Then run `merge` with `{"task":"id","closes":[12],"head":"full-sha-from-merge-check","told":[],"method":"merge"}`. `told` records other orchestrators informed of the merge, if any. Do not send external messages without authorization. Method may be merge, squash or rebase. `onRedMain:true` is only for the task that repairs the failing base.
4. The adapter repeats live checks under its repository lock, verifies the expected head, claims the merge persistently, and submits the merge pinned to that SHA. A changed PR, head or target base requires another review and owner approval; the recorded approval is cleared when the merge is confirmed complete; a refused or uncertain request does not require repeating an unchanged approval. A server-enforced protection rule remains authoritative.
5. If the write outcome is uncertain, do not retry the merge. Run `reconcile`, which only reads GitHub and adopts a confirmed merge. If GitHub still reports the PR unmerged, inspect it and use `reconcile` with `{"release":true}` only after the original request has settled (at least two minutes). A stale claim is never automatically cleared in the current run.
6. After a confirmed merge, read the base branch's checks and keep checking in this task until they settle. Report a failure as a blocker; do not call the run done until warnings/blockers are addressed. There is no background watcher after the chat stops.

The adapter serializes its own writes across runs in this project, but cannot lock other tools or external actors. GitHub's pinned head protects the PR revision, not a moving base branch. Protection rules should enforce any required up-to-date-base policy.
